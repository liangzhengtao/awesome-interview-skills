# Coding Interview Framework — 编码面试框架

> **When to Use / 使用场景**: 在现场编码面试中，用结构化方法解决编程问题，避免慌乱和遗漏。

---

## Key Concepts / 核心概念

### UMPIRE 方法

面试不是比谁写代码最快，而是比谁的解题过程最清晰。UMPIRE 是一个经过验证的 6 步框架：

| 步骤 | 英文 | 中文 | 时间分配 |
|------|------|------|---------|
| U | Understand | 理解题目 | 2-3 min |
| M | Match | 匹配模式 | 1-2 min |
| P | Plan | 制定计划 | 2-3 min |
| I | Implement | 编码实现 | 10-15 min |
| R | Review | 检查代码 | 2-3 min |
| E | Evaluate | 评估优化 | 2-3 min |

---

## Step-by-Step Framework / 分步详解

### Step 1: Understand 理解题目 (2-3 min)

**目标**: 确保你完全理解了问题，没有遗漏关键信息。

#### Checklist

```
□ 用自己的话复述问题
□ 确认输入的类型和范围
□ 确认输出的格式
□ 要求 2-3 个具体例子（含边界情况）
□ 确认约束条件
□ 询问是否有时间和空间复杂度要求
```

#### 话术模板

```
"让我确认一下题目的要求：
 - 输入是 [类型]，代表 [含义]
 - 我需要返回 [输出格式]
 - 例如，如果输入是 [例子]，那么输出应该是 [结果]
 - 对于边界情况，如果 [边界]，我应该返回 [处理方式]
 这样理解正确吗？"
```

#### 常见确认问题

```
- 数组是否可能为空？
- 是否有重复元素？
- 数值范围？是否会溢出？
- 是否需要处理无效输入？
- 返回所有解还是任意一个解？
- 是否需要原地修改？
- 是否需要考虑并发？
```

---

### Step 2: Match 匹配模式 (1-2 min)

**目标**: 将问题归类到已知的算法模式。

#### 快速匹配流程

```
这道题的核心操作是什么？
│
├─ 排序？ → 考虑排序后简化问题
├─ 查找？ → Binary Search / Hash Map
├─ 遍历？ → BFS / DFS / 遍历模板
├─ 子数组/子串？ → Sliding Window / Two Pointers
├─ 最优解？ → Dynamic Programming / Greedy
├─ 所有组合？ → Backtracking
├─ 有序维护？ → Stack / Heap / BST
└─ 图/连通性？ → BFS / DFS / Union Find
```

#### 话术模板

```
"这道题看起来像是一个 [模式名称] 问题，
因为 [推理原因]。
我之前解决过类似的问题，比如 [类似题目]。"
```

---

### Step 3: Plan 制定计划 (2-3 min)

**目标**: 在写代码之前，先制定清晰的解题计划。

#### 计划模板

```
我的解题思路：
1. 首先，[第一步操作]
2. 然后，[第二步操作]
3. 接着，[核心逻辑]
4. 最后，[返回结果]

时间复杂度: O(?)
空间复杂度: O(?)

让我用一个例子来验证：
输入: [具体例子]
Step 1: [中间结果]
Step 2: [中间结果]
Step 3: [最终结果] ✓
```

#### 话术模板

```
"我的计划是：
首先...（这步的目的是...）
然后...（利用了...特性）
最后...（返回...）

预期时间复杂度是 O(?)，空间复杂度是 O(?)
让我用你给的例子 [例子] 验证一下..."
```

---

### Step 4: Implement 编码实现 (10-15 min)

**目标**: 把计划转化为可运行的代码。

#### 编码原则

```
1. 先写框架，再填细节
2. 变量名要有意义（不要用 x, y, z）
3. 适当添加注释（不是每行都注释）
4. 一次只关注一个部分
5. 遇到 bug 不要慌，慢慢调试
```

#### 编码模板

```python
def solve(input):
    # Step 1: 处理边界情况
    if not input:
        return []

    # Step 2: 初始化变量
    result = []
    # ... 初始化 ...

    # Step 3: 核心逻辑
    # 这里是主循环/递归
    for ... in ...:
        # [核心操作]
        pass

    # Step 4: 返回结果
    return result
```

#### 如果卡住了怎么办

```
1. 不要沉默！说出你的思路
2. 退一步，用更小的例子手动模拟
3. 问面试官："我可以先写一个暴力解法吗？"
4. 从暴力解法出发，寻找优化点
5. 面试官通常会给提示，注意倾听
```

#### 话术模板

```
"我现在开始写代码。
[边写边解释]
这里我用了 [数据结构]，因为 [原因]。
这部分是 [功能]...
...

代码写完了，让我来检查一下。"
```

---

### Step 5: Review 检查代码 (2-3 min)

**目标**: 用具体测试用例验证代码，找出 bug。

#### 检查清单

```
□ 用题目的例子手动走一遍代码
□ 检查边界情况
□ 检查 off-by-one 错误
□ 检查变量是否正确初始化
□ 检查循环终止条件
□ 检查返回值
□ 检查是否有未处理的 None/null
```

#### 手动追踪模板

```
输入: [例子]
初始化: 变量状态 = ...

第 1 轮循环:
  - 当前元素: ?
  - 条件判断: ?
  - 变量更新: ?
  - 状态: ...

第 2 轮循环:
  ...

最终输出: [结果] ?=? 期望输出
  → ✓ 正确 / ✗ 错误，问题在...
```

#### 常见 Bug 类型

| 类型 | 描述 | 检查方法 |
|------|------|---------|
| Off-by-one | 循环边界错误 | 检查 `<` vs `<=` |
| Null reference | 未检查空值 | 检查所有指针/节点访问 |
| Index out of bounds | 数组越界 | 检查索引计算 |
| Infinite loop | 循环不终止 | 检查循环变量是否正确更新 |
| Wrong initialization | 初始值错误 | 对比第一轮和预期 |

---

### Step 6: Evaluate 评估优化 (2-3 min)

**目标**: 分析复杂度，讨论可能的优化。

#### 评估模板

```
当前解法:
- 时间复杂度: O(?)
- 空间复杂度: O(?)

可能的优化:
1. 如果用 [数据结构/算法] 替代 [当前方案]，
   可以将 [某操作] 从 O(?) 优化到 O(?)
2. 如果允许修改输入，可以省去 [操作]，空间降到 O(1)

Trade-off:
- [优化方案] 的代价是 [代码复杂度/可读性/...]
```

## 边界情况检查清单

### 数组
```
□ 空数组 []
□ 单元素 [x]
□ 两个元素 [x, y]
□ 全部相同 [x, x, x, ...]
□ 已排序 / 逆序
□ 包含负数 / 零
□ 非常大的数组
```

### 链表
```
□ 空链表 None
□ 单节点
□ 两个节点
□ 环形链表
□ 所有节点值相同
```

### 字符串
```
□ 空字符串 ""
□ 单字符
□ 全部相同字符
□ 包含空格/特殊字符
□ 大小写敏感性
```

### 树
```
□ 空树 None
□ 只有根节点
□ 只有左子树/只有右子树
□ 完全二叉树
□ 退化为链表的树
```

### 图
```
□ 空图
□ 单节点
□ 不连通的图
□ 有环图
□ 自环
□ 重复边
```

### 数值
```
□ 0
□ 负数
□ INT_MAX / INT_MIN
□ 溢出情况
□ 浮点精度
```

## Common Mistakes / 常见错误

1. **上来就写代码**: 跳过理解步骤，写到一半发现理解有误
2. **沉默编码**: 写代码时不说话，面试官无法了解你的思路
3. **死磕一道题**: 卡了 5 分钟还没进展，应该寻求提示
4. **不验证代码**: 写完就提交，不手动走测试用例
5. **忽略边界情况**: 只考虑正常输入，忽略空值、溢出等
6. **变量名含糊**: 用 `x`, `temp`, `flag` 等无意义命名
7. **不分析复杂度**: 面试官期望你能分析时间和空间复杂度
8. **直接给最优解**: 应该先说暴力法，再讨论优化

---

## Pro Tips / 高手技巧

- **时间管理**: 45 分钟面试，前 5 分钟理解，中间 25 分钟编码，最后 10 分钟检查优化
- **先写伪代码**: 如果时间紧张，先写伪代码确认思路
- **用具体例子驱动思考**: 不要在脑子里跑抽象逻辑，用具体数字
- **主动说出你的思考**: "我现在在想是否可以用..."
- **承认不确定性**: "我不太确定这个边界情况，让我想想..."
- **充分利用面试官**: 他们希望你成功，通常会给有帮助的提示
- **写完后主动检查**: 不要等面试官说 "你的代码有问题"
- **保持冷静**: 遇到 bug 是正常的，冷静调试比慌乱重写更好

## Practice Questions / 练习建议

### 每日练习流程

```
1. 选一道 Medium 难度题目
2. 设置 25 分钟计时器
3. 按 UMPIRE 框架解题
4. 对答案，分析差距
5. 如果超过 25 分钟还没解出来，看提示
6. 记录到错题本
```

### 推荐练习题目

| 难度 | 题目 | LeetCode # | 核心技巧 |
|------|------|-----------|---------|
| Easy | Valid Parentheses | 20 | Stack |
| Easy | Two Sum | 1 | Hash Map |
| Medium | 3Sum | 15 | Two Pointers |
| Medium | Group Anagrams | 49 | Hash Map |
| Medium | Binary Tree Level Order | 102 | BFS |
| Medium | Product of Array Except Self | 238 | Prefix/Suffix |

> **面试的本质不是考试，而是一次协作解决问题的过程。** 面试官想看到的是你如何思考、如何沟通、如何应对不确定性。UMPIRE 框架帮助你展示所有这些能力。
>
> The interview is not a test — it's a collaborative problem-solving session. The interviewer wants to see HOW you think, communicate, and handle uncertainty. UMPIRE helps you showcase all of these.
